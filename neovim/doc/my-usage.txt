Keymaps							*my-commands*

Every keymap has a description, so the current list is always available
through the keymap picker: `<space>fk`. Keymaps use a prefix per area:

	`<space>`	Pickers
	`\`		LSP (buffer local), Termdebug `\d*`, smart-yank `\o*`,
			render-markdown `\rt`, swap parameters `\a`
	`,`		Debugging (DAP)
	`;`		Git: gitsigns `;h*`, git-conflict `;r*`
	`[x` `]x`	Motions: `t` tabs, `h` hunks, `r` conflict panes,
			`e` errors, `m` functions, `,` parameters
	`<C-*>`		`<C-b>` explorer, `<C-f>` floating terminal,
			`<C-h>` highlighter, `<C-j>` :make

Neovim's own defaults are kept for `[q` `[l` `[a` `[d` and friends.

PLUGIN NOTES						*my-plugins*

------------------------------------------------------------------------------
lsp setup						*my-lsp-setup*

Server configs live in `lsp/<server>.lua`, and every server with a file there
(or in `local/lsp/`) is enabled. Keymaps, completion and reference
highlighting are set up for every server by an |LspAttach| handler in
`lua/lsp/init.lua`. LSP keymaps are prefixed with `\`.

Project specific settings go in a `.nvim.lua` in the project root, which is
sourced since 'exrc' is set. Neovim asks once before trusting it, see
|:trust|. Call |vim.lsp.config()| from it, and the settings are merged on top
of the shared config: >
	vim.lsp.config('clangd', {
	    cmd = { 'clangd', '--compile-commands-dir=build/debug' },
	})
<
An `lsp/clangd.lua` in the project root is not read by itself. It's only read
if the project directory is on 'runtimepath', for example by adding this to
`.nvim.lua`: >
	vim.opt.rtp:prepend(vim.fn.getcwd())
<
Tables, like `settings`, are merged key by key, while lists, like `cmd`, are
replaced. See |lsp-config-merge|.

------------------------------------------------------------------------------
Theme							*my-colorscheme-setup*

The theme is `lua/theme/mini-theme.lua`. It derives the colors from a base
background and foreground, using `mini.colors` to work with hue, saturation
and lightness. If mini.nvim isn't installed, `lua/theme/fallback.lua` is used
instead. It sets a smaller set of highlights based on the background
brightness, `$BACKGROUND` set to "light" or "dark".

------------------------------------------------------------------------------
DAP							*my-dap-setup*

Debug adapter protocol allow for more flexible debugging. The benefit over
termdebug is that this isn't limited to gdb, and enables the use of python
debugging etc

In addition, this allows for some more flexible debugger setup based on the
`launch.json` files used by VS code. This is described in |dap-launch.json|
For example these can look like >
	{
	    "version": "0.2.0",
	    "configurations": [
		{
		    "name": "Debug program-file",
		    "type": "gdb",
		    "program": "build/program-file",
		    "request": "launch"
		},
		{
		    "name": "Debug remote session, locally",
		    "type": "gdb",
		    "program": "build/program-file",
		    "request": "attach",
		    "target": "localhost:2345"
		}
	    ]
	}
<
The configuration is done in `lua/setup/debug.lua`

==============================================================================
LUA SETUP  						*my-lua-setup*

`init.lua`
			Entry point. Runs bootstrap, core options, keymaps and
			autocmds, packages, theme and LSP, and then all plugin
			specs.

`lua/core/`
			`bootstrap.lua`: paths, local config, dev plugins, `$PROF`
			and `$BACKGROUND`. `options.lua`, `keymaps.lua` and
			`autocmds.lua`: setup that doesn't depend on plugins.
			`pack.lua`: the |vim.pack| package list. `util.lua`:
			`try_load()` and `map()`.

`lua/setup/`
			Plugin setup, one file per area: `ui.lua`, `language.lua`,
			`debug.lua` and `git.lua`. Every file in the directory is
			loaded. Each file returns a list of specs: >
			  {
			      module = 'gitsigns',
			      setup = function(gitsigns) ... end,
			  }
<			The module is loaded with `try_load()`, so a missing or
			broken third party plugin is skipped. Specs for own
			plugins have no `module`, and their `setup()` is always
			called, so bugs in own code fail loudly. The keymaps for a
			plugin live in its spec.

`lua/plugins/`
			Own plugins: smart-yank, visual-match and git-conflict.

`lua/theme/`, `lua/lsp/`, `lsp/`
			See |my-colorscheme-setup| and |my-lsp-setup|.

==============================================================================
LOCAL CONFIG						*my-local-config*

Machine specific config goes in `local.lua` and `local/`, both gitignored.
Copy `local.lua.sample` to get started. All keys are optional:

	`packages`	Extra |vim.pack| specs
	`dev`		Working trees of plugins under development. They're
			used in place, so edits show up on the next start
	`after_options`	Hook that runs after core options, before plugins
	`after_all`	Hook that runs last. Use `packadd!` here, since a
			plain `packadd` loads the package twice

`local/` is added to 'runtimepath', and is used for:

	`local/lua/setup/`	Plugin specs, loaded like `lua/setup/`
	`local/lsp/`		Servers for this machine only, enabled
				automatically
	`local/after/lsp/`	Changes to a shared server, merged on top of
				`lsp/<server>.lua`
	`local/after/ftplugin/`	Filetype changes

Errors in `local.lua`, and `dev` paths that don't exist, stop startup.
